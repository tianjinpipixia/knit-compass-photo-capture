# DoCLASSEの累積保存まで含む重複排除・保全確認（2026-10-17）

PR #274の統合後に累積正本まで照合したところ、日次処理で共通商品コードを統合しても、既存の累積正本を復元する際に色別URLが再追加される経路を確認した。また、旧記録には色番号を含まない `/item/detail/1_1_商品番号` もあり、色番号付きURLだけを照合する実装では初回発見と誤認し得た。

累積正本の取得時点のDoCLASSE shard（blob `849c122c8eb8ad032676b3a0b5399b27996fa8cb`）は267レコード/254共通商品コードだった。これは別商品の欠落ではなく、旧URL・色違いによる13レコードの重複を含む。

## 修正

- 公式DoCLASSEの色番号なし/ありURLだけを同じ共通商品コードとして照合する。他ホストの商品識別は従来のURLを維持する。
- 作業状態と累積正本の復元・統合・再出力まで同じ識別を使用し、復元時の色重複の再発を防ぐ。
- 代表URLは実在する公式商品URLを使う。元URLはsource_url_aliases、元の各レコードの事実はlegacy_identity_records、掲載証拠はlisting_evidenceに保持する。初回観測日は最古、最終観測日は最新を保つ。色ごとの混率等が同じだとは推測しない。
- 正本の保全チェックでは、代表URLが変わった場合も、同じブランド・同じDoCLASSE商品番号で、旧URL・別名URL群・元の全事実・過去の保存事実が完全に保持されている場合だけを認める。別ブランド、別商品、事実の欠落・改変では保全成立としない。
- PUBLISH_HOLD、Human Review Required、完全収集判定、正式未処理日台帳を変更しない。

## 検証

- 上記実データを隔離した一時ディレクトリで復元・出力：267レコード→254商品。元267レコードすべての事実が代表記録または保存履歴に完全一致して残り、欠落0。空の作業状態から再起動・再出力しても結果は一致。本番ファイルへの手動書き込みはしていない。
- 回帰試験は色URL3件/共通商品1件、色番号なし旧URL、追加色の初回発見誤認防止、素材などの相違する旧事実、全証拠・最古/最新観測日、累積復元時の再重複防止、再起動の安定性を確認。
- 他ホストでcolorクエリが異なるURLは別のまま。保全例外はDoCLASSEだけで、同じ商品番号でも別ブランドや旧事実の改変を拒否する。
- 全 `test_brand64*.py`：140件成功（ローカル）。

件数減はURL重複の統合であり、新規取得や削除、完全収集の成立を意味しない。通常の日次実行での回復件数や取得制限は別途確認する。
